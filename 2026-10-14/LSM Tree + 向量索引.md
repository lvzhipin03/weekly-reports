## 背景
### 什么是 LSM TREE
将频繁、随机的数据更新，尽可能转化为内存中的修改和磁盘上的批量顺序写入，再通过后台 Compaction 整理数据。

### 为什么会出现 LSM TREE
传统的大规模有序数据结构（例如 B+ 树），当插入或修改一条数据时，需要将磁盘中的相应数据读到内存。逻辑上有序的修改和插入，不一定对应于物理上连续的存放位置。在频繁更新场景下，大量的随机 IO 成本很高。

### 核心优势
1. 适合高吞吐写入

它将大量分散写入缓冲成批量操作（把随机写缓冲成顺序写），避免每次写入都立即修改磁盘上的大型有序结构。 不过，持续写入速度最终仍受 Compaction 吞吐限制，后台合并跟不上就可能出现写入停顿。

### 代价
1. 写放大

不断 compaction 导致一条数据在磁盘中可能多次重写。

2. 读放大

数据存在多个层级中，导致一次逻辑查询可能需要访问多个结构或文件。

3. 空间放大





## 倒排索引
### 是否有引入必要
LSM-Tree 的主要优势之一，是通过内存缓冲和批量写入，将频繁的随机更新转换为更高效的顺序写入。

在大规模动态向量检索场景下，向量索引的更新主要包括向量插入、删除以及修改。

对于 IVF 索引，其结构主要包括聚类中心和倒排列表。聚类中心通常在索引训练完成后保持固定，不需要随每次向量插入或删除而更新。因此，索引的动态维护主要集中在倒排列表上。

对于向量插入，可以将每个倒排列表组织为多个数据块，新向量只需要追加到对应的数据块中。当数据块写满时，再分配新的数据块，从而避免频繁扩容和搬迁整个倒排列表。

对于向量删除，可以采用删除位图记录删除状态，并在后台定期批量清理失效数据，避免每次删除都立即修改和整理倒排列表。

因此，IVF 的插入和删除操作可以通过分块追加、内存缓冲和延迟清理等机制进行优化，不一定需要引入完整的 LSM-Tree。

## 图索引
### 是否有引入必要
对于图索引，除了向量的插入，删除之外。每次节点插入，删除导致的邻居关系变化会有大量的随机写 IO。

举一个简单的例子，对于 HNSW 算法，第 0 层的节点。每一个节点都有 2M 个邻居（这里假设 M=32）。插入一条向量 va，在第 0 层，需要将 va 的邻接关系（64 个节点 id）全部写入磁盘中。这部分是顺序写。另外，需要将涉及到的 64 个邻居节点的邻接关系进行更新和修改。这部分涉及到的全部是随机 IO，大概有 64 次随机写。

这些随机写正是 LSM TREE 可以优化的地方，也就是将邻接关系使用 LSM TREE 的方式进行组织，将大量的邻接关系更新带来的随机写转变为顺序写。代价是在读取临界关系时，存在一定的读放大。

### 量化分析
对于一亿条向量，每个 float 的大小是 4 字节，每个邻居关系中 id 存储大小也是 4 字节。M=32，HNSW 的第 0 层图结构，向量维度为 768 维。

邻接表大小为：$ 
N\times2M\times4 = 25.6 \ GB $

向量大小为：$ 307.2 \ GB $

### 是否为主要瓶颈
对于图索引，插入向量实际上时查询最近邻作为第一步，正向剪枝和反向剪枝作为第二步，也就是说插入向量有大量的查询需求。在内存空间不足以放下所有向量+邻居关系时，查询最近邻导致的随机读开销巨大（剪枝操作要读的向量+邻居关系在第一步查询时已经读入内存）。此时需要借助量化，在内存中常驻 PQ，SQ，RABITQ 量化向量来做两阶段搜索，以减少大量随机读。此时随机 IO 就集中在查询最近邻的第二阶段，精排，以及剪枝所需要的精确向量中了。

也就是说，无论如何，在大规模数据向量索引（面向磁盘索引），插入向量本身已经有严重的随机读 IO 开销。在没有实际测试之前，我认为整个插入向量的瓶颈不一定在剪枝后的邻居关系更新带来的随机写 IO 上。

#### 量化分析
有一条要插入的向量，768 维。库中有一亿条向量，设置 ef_search=100。

在原来的项目中，10W 数据下，99% 召回率，大概要设置 ef_search=100，每一步大概要读 30 个向量。

要读的向量数量，假设每一步要读 45 个（随着向量数量变多，在相同召回率要求下，ef_search 和 每一步要读的向量都要增加）。假设所有的向量都不在内存中。

总共随机读向量数量大约要读：100 × 45 = 4500 个向量

邻居关系写入数量：2M = 64 个邻居关系



4500 个向量，每个向量 768 维，在 4kb 的页面上两条向量同时在同一个页面上的概率比较低，总共要读的向量大小：4500 × 4 KiB = 18000 KiB

64 个邻居关系，假设所有邻居关系都不再同一页上，64 × 4 KiB = 256 KiB



如果使用了类似 PQ 的量化技术，使用冗余计算减少了要随机读取的向量大小。比如从 4500 降低到了 500，这已经比较乐观（因为大规模向量索引必然导致内存压力很大，导致 PQ 的精度不高，导致精排向量的数量剧增）。

18000 KiB / 9 = 2000 KiB

所以至少，随机读的大小都是随机写的至少 8 倍。在 NVME SSD 中，随机读大概是随机写的 3-8 倍（AI 给出的判断，没有实际测试）。在这个值是 5 倍情况下，随机读所消耗的设备服务能力仍约为随机写的 1.56 倍。换句话说，插入向量的主要瓶颈仍然在随机读，随机写的开销可能和随机读相当，或者低于随机读。



另外，把邻居关系放入 lsm-tree 还会导致，在读邻居关系时，产生读放大。



综上，我认为引入 LSM TREE 在一定条件下有一定的作用，但并不会让插入性能倍数提升。

具体性能数据还需要进一步实验验证。

### 目前的研究进展
#### LSM-VEC: A Large-Scale Disk-Based System for Dynamic Vector Search
这篇文章，跟之前我讲的一样，都是只用 LSM TREE 作为邻居关系的存储方式。

这篇论文提出了一种基于 LSM-Tree 的动态磁盘向量检索系统 LSM-VEC，主要解决大规模图向量索引中，动态更新成本高、内存占用大以及磁盘随机 I/O 开销高的问题。

传统 HNSW 通常需要将图结构放在内存中，而 DiskANN 虽然支持磁盘存储，但动态更新和图结构维护的成本较高。

针对这些问题，论文主要提出了三个优化。

**第一，基于 LSM-Tree 的动态图索引存储。**

将 HNSW 的上层图保留在内存中，底层图存储在磁盘上，并使用 AsterDB 这种图专用 LSM-Tree 管理邻接关系。

插入向量时，将新增或修改的邻接关系作为 KV 记录写入 LSM-Tree，通过内存缓冲和后台 Compaction，将大量随机写转化为批量顺序写。

**第二，基于采样的邻居过滤。**

由于磁盘图搜索需要大量随机读取原始向量，论文采用类似 SimHash 的随机投影方法，为每个向量生成内存中的二进制编码。

搜索过程中，先利用编码估计邻居与查询向量的相似度，过滤掉不太可能成为近邻的节点，从而减少原始向量的随机读 I/O。

**第三，基于查询访问模式的图重排序。**

根据实际查询过程中节点的共同访问情况，调整向量在磁盘上的物理布局，将经常一起访问的向量放在相邻位置，从而提高数据局部性，减少随机 I/O。

在实验方面，论文使用了 SIFT1B 的一亿条向量子集。相比 DiskANN，在纯插入负载下，LSM-VEC 的平均更新延迟从 12.5 毫秒（diskann）降低到 4.9 毫秒（lsm-vec），约提升 2.6 倍，同时显著降低了内存占用。

#### CLIP: Lightweight Cosine-Law-Based Inverted-List Pruning for IVF-Based Vector Search
暂时没有发表，由香港浸会大学、上海交通大学和腾讯联合完成，目前是 2026 年发布的 arXiv 预印本。

**第一，提出 CLIP 剪枝算法。**

传统 IVF 在查询时，需要选择 nprobe 个聚类，并扫描这些聚类中的所有向量，计算开销比较大。

作者基于余弦定律构建距离下界，提出了聚类间剪枝和聚类内剪枝。

其中，聚类内剪枝要求倒排列表按照向量到聚类中心的距离排序，这样就可以通过二分查找确定需要扫描的向量范围，减少距离计算。

**第二，提出 IVF-CLIP 和 HIVF-CLIP。**

作者将 CLIP 分别应用于普通 IVF 和层次化 IVF。其中，HIVF-CLIP 通过多层聚类结构，进一步减少查询时需要访问的聚类数量。

**第三，提出 LSM-IVF，解决动态更新问题。**

因为 CLIP 要求倒排列表有序，所以频繁插入向量会带来额外的索引维护开销。

作者借鉴 LSM-Tree 的思想，设计了多层向量索引结构。

L0 是内存 Buffer，用来快速接收新向量；L1 使用 IVF-CLIP；更深的层级使用 HIVF-CLIP。

当 Buffer 达到阈值时，后台通过 Compaction 将新增向量合并到下一层。

由于文章面向的是插入场景，实际上不同层之间的桶id，不会重复。如果要面向 更新/删除 桶id，就会重复。

由于倒排列表本身按照聚类中心距离排序，可以利用 Merge Sort 批量维护索引，避免每次插入都立即调整磁盘上的有序列表。

另外，传统 LSM 分层查询可能需要逐层搜索，再合并 Top-K。

LSM-IVF 则使用全局候选聚类队列，统一管理不同层级的搜索过程，并利用 CLIP 进行剪枝，降低跨层查询开销。

**实验方面，** LSM-IVF 在动态负载下，相比 SPFresh 和 Quake 等方法，混合操作吞吐量最高提升 141%，同时保持较高的 Recall。计入后台 Merge 后，其摊销更新成本与 Quake 接近。
